# 吃饭分账微信小程序设计规格

日期：2026-07-31

## 1. 产品目标

为同事聚餐提供一个无需登录、无需服务器、可以快速录入并准确结算的微信小程序。它需要正确处理多人分别垫付、全员均摊、部分人员均摊和个人消费，并以一眼可执行的方式告诉每个人应当向谁转多少钱。

成功标准：

- 用户能在一分钟内完成一次五人、三笔消费的账单录入。
- 任何结算结果中，所有人的最终承担金额之和必须等于实际总消费。
- 用户无需自行计算垫付款抵扣关系。
- 结果页能直接用于口头通知或复制到微信群。

## 2. 第一版范围

第一版包含：

- 微信原生小程序。
- 2–20 名参与人。
- 自动字母 A–T 与手动姓名两种参与人模式。
- 多笔消费记录，每笔包含金额、付款人、承担人和可选备注。
- 默认全员均摊，也可选择一人或多人承担。
- 自动选择主收款人，并允许用户手动更换。
- 行动清单式结算结果。
- 可复制的微信群结算文案。
- 当前账单的本地自动保存与恢复。

第一版不包含：

- 用户登录或微信联系人读取。
- 多人实时编辑同一账单。
- 云数据库、跨设备同步或历史账单列表。
- 微信支付、代收款或自动转账。
- 按菜品数量、比例、权重或百分比拆分。
- 应用内语音识别或自然语言账单解析。这类功能依赖云端服务并产生按量调用成本，不符合第一版零服务器费用的约束。

## 3. 核心用户流程

### 3.1 创建账单

用户打开小程序后选择参与人录入方式：

1. “快速字母”是默认方式。用户调整人数，系统自动生成 A、B、C……。
2. “输入姓名”允许逐个添加本次参与人的姓名。姓名只保存在当前账单中。

参与人数至少为 2，最多为 20。自定义姓名必须非空且互不重复。

### 3.2 记录消费

创建参与人后进入单页账本。账本顶部显示参与人数、消费总额、消费笔数和预计主收款人。用户点击“记一笔”打开消费编辑面板，依次填写：

- 金额：必填，最小 0.01 元。
- 付款人：必选一人。
- 备注：可选，例如“平台套餐”“C 的饮料”。
- 承担人：默认全员，也可切换为指定的一人或多人。

账本以列表展示全部消费。每条记录清楚显示备注、付款人、承担范围和金额，并支持编辑和删除。任何变更都立即刷新汇总数据。

### 3.3 查看结算

至少存在一笔有效消费后，用户点击“算一算怎么转账”。结果页顶部显示主收款人、主收款人净应收金额、总消费和人数。下方以行动清单逐行显示：

- 谁转给谁。
- 转账金额。
- 简短解释，例如“已抵扣垫付 ¥70”或“含自己的饮料 ¥10”。

用户可返回修改账单，也可复制格式化后的微信群结算文案。

## 4. 视觉与交互方向

整体采用“石墨极简”方向：

- 黑、白、灰为主体，微信兼容的系统字体。
- 蓝色只用于可点击操作、选中状态和轻提示。
- 通过字号、留白和卡片层级组织信息，避免装饰性图形干扰金额。
- 圆角适中，阴影克制，金额使用等宽数字表现以便纵向比较。
- 触控区域不小于 44px，主要操作按钮固定在页面内容底部的自然位置，不遮挡列表。

确定的页面结构：

- 参与人页：分段选择“快速字母 / 输入姓名”。
- 账本页：单页账本式，而非逐步向导式。
- 结果页：行动清单式，而非关系图式。

## 5. 技术架构

第一版使用微信原生小程序的 WXML、WXSS 和 JavaScript，不依赖后端服务。

主要页面：

- `pages/start`：创建参与人。
- `pages/ledger`：展示和编辑消费账本。
- `pages/result`：展示结算结果与分享文案。

主要业务模块：

- `services/settlement`：纯函数式分账与结算引擎，不依赖页面状态。
- `services/storage`：当前账单的本地保存、读取、校验和清除。
- `utils/money`：元与分转换、金额格式化和输入校验。

主要可复用组件：

- 消费编辑面板。
- 承担人选择器。
- 参与人头像或字母标识。
- 转账行动行。

页面只负责采集输入和渲染结果，所有金额计算集中在分账引擎中，保证算法可独立测试。

## 6. 数据模型

账单结构：

```js
{
  id: "local-draft",
  participantMode: "letters" | "names",
  participants: [
    { id: "p1", displayName: "A" }
  ],
  expenses: [
    {
      id: "e1",
      amountCents: 39800,
      payerId: "p1",
      splitMode: "all" | "selected",
      participantIds: ["p1", "p2"],
      note: "平台套餐"
    }
  ],
  collectorId: "p1",
  updatedAt: 1785480000000
}
```

`amountCents` 始终使用整数分，禁止使用浮点金额作为持久化值。参与人使用稳定 ID，显示名可修改而不会破坏已有消费引用。

当 `splitMode` 为 `all` 时，消费始终随当前参与人列表重新计算；当它为 `selected` 时，只由明确保存的参与人承担。

## 7. 分账算法

### 7.1 应承担金额

每笔消费只在其承担人之间平均拆分。计算以分为单位：

1. `基础份额 = 金额分数 ÷ 承担人数` 的整数部分。
2. 余下的分按参与人在账单中的顺序依次补 0.01 元。
3. 每笔消费拆分后的总和必须等于该笔消费金额。

因此除不尽时，参与人的差异最多为 0.01 元，且结果可重复、可解释。

### 7.2 已垫付金额与净额

对每个人分别汇总：

- `已垫付金额`：其作为付款人的全部消费之和。
- `应承担金额`：各笔消费分配给他的份额之和。
- `净额 = 已垫付金额 - 应承担金额`。

净额大于零表示应收，净额小于零表示应付，等于零表示无需转账。所有参与人的净额之和必须为零。

### 7.3 主收款人结算

默认主收款人从“净额大于零”的参与人中选择实际付款总额最高的人；付款额相同时按参与人顺序选择。这样通常仍是实际付得最多的人，同时避免把最终仍需付款的人标成“收款人”。用户可以在净额大于零的参与人中手动更换主收款人。如果所有人的净额都为零，结果页显示“已经结清”，不设置主收款人。

所有结算通过主收款人完成：

- 非主收款人的净额为负时，该人向主收款人支付绝对值金额。
- 非主收款人的净额为正时，主收款人向该人支付该金额。
- 净额为零的人不生成转账动作。

这种方式最多产生 `参与人数 - 1` 笔转账，优先满足“由付得最多的人统一算钱和收款”的真实习惯。

## 8. 已确认的计算案例

### 案例一

- A 支付 398 元套餐，全员承担。
- B 支付 60 元菜品，全员承担。
- B 另支付 10 元饮料，只由 C 承担。
- 共 5 人。

结果：

- B → A：21.60 元。
- C → A：101.60 元。
- D → A：91.60 元。
- E → A：91.60 元。
- A 共收回 306.40 元。

### 案例二

- A 支付 390 元餐费，全员承担。
- B 支付 60 元啤酒，全员承担。
- C 支付 50 元打车费，只由 A、B、C 承担。
- 共 5 人。

公共费用每人 90 元。打车费按参与人顺序拆为 A 16.67 元、B 16.67 元、C 16.66 元。

结果：

- B → A：46.67 元。
- C → A：56.66 元。
- D → A：90.00 元。
- E → A：90.00 元。
- A 共收回 283.33 元。

## 9. 参与人变更规则

开始记账后仍可返回修改参与人：

- 修改显示名不会影响账单计算。
- 新增或删除参与人会提示“全员均摊项目将重新计算”。
- 新增参与人会自动加入所有 `splitMode: "all"` 的消费，不会加入 `selected` 消费。
- 删除参与人会将其从承担范围中移除。
- 如果待删除参与人是任一消费的付款人，必须先更改该消费的付款人或删除该消费。
- 任何消费都不能在变更后出现零名承担人。

## 10. 校验、异常与恢复

- 参与人数不足、姓名为空或重复时禁止进入账本。
- 金额为空、为零、为负数或格式非法时禁止保存消费。
- 付款人或承担人缺失时禁止保存消费。
- 没有消费时禁用“算一算怎么转账”。
- 解析本地草稿失败时丢弃损坏草稿并安全返回创建页，不展示未经校验的计算结果。
- 清空或开始新账单前弹出确认，避免误删当前记录。
- 页面展示金额前再次校验结算守恒：总应付等于总消费，净额之和为零。

## 11. 本地存储与隐私

每次账单变化后，将经过校验的当前草稿写入微信本地存储。重新打开小程序时提示用户继续上次账单或开始新账单。第一版不上传数据、不读取微信联系人、不申请定位，也不保存真实支付信息。

## 12. 测试策略

### 自动化测试

分账引擎使用纯 JavaScript 单元测试覆盖：

- 全员均摊。
- 单人消费。
- 部分人员均摊。
- 多人分别垫付。
- 金额不能整除时的分币规则。
- 非主收款人仍有净应收款。
- 无需转账的参与人。
- 两个已确认案例的精确结果。
- 总应付守恒与净额守恒。
- 非法输入拒绝。

本地存储模块覆盖正常恢复、版本不匹配和损坏草稿处理。

### 页面与人工验证

- 在微信开发者工具中验证首页、账本、编辑面板和结果页的主要操作路径。
- 验证常见手机宽度、长姓名、20 人和多笔消费下的滚动与布局。
- 验证退出再进入后的草稿恢复。
- 验证复制群聊文案的格式与金额。

## 13. 后续扩展方向

设计保留但第一版不实现：常用同事、历史账单、按比例拆分、账单分享链接、多人协作和云同步。这些能力不得影响第一版的单人快速录入路径。语音录入只有在未来存在成本可控且不需要开发者承担持续调用费用的方案时才重新评估。
